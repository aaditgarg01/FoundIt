1. PLANNING PHILOSOPHY
================================================================================

------------------------------------------------------------------------------
1.1 Database First, and Genuinely First
------------------------------------------------------------------------------

The sequencing principle that governs this plan is that the data model is built,
normalised, indexed and tested before a single line of user interface is
written. This is not the natural instinct. The natural instinct is to build a
screen, because a screen is visible and a schema is not, and progress that
cannot be seen feels like no progress.

The instinct is wrong here for three reasons.

Schema changes are expensive downstream. A column added in week two costs a
migration. The same column added in week six costs a migration, a repository
change, a service change, an API contract change, a client type change, a form
field, a validation rule and a test update. The cost multiplier is roughly the
number of layers already built on top.

The schema is the deliverable. This is a database systems project. A beautiful
interface over a denormalised schema scores badly; a plain interface over a
rigorous schema scores well. The effort should follow the marks.

The hard problems are all in the data layer. Matching, concurrency, integrity
and audit are the four genuinely difficult parts of FoundIt, and all four are
database problems. Solving them first means the remaining work is
straightforward, and a project whose hard parts are finished early is a project
that can absorb a bad week.

------------------------------------------------------------------------------
1.2 Vertical Slices Within Phases
------------------------------------------------------------------------------

Within each phase after the first, work proceeds in vertical slices — one
feature taken from schema through repository, service, API and test before the
next begins. Horizontal layering, in which every repository is written, then
every service, then every controller, defers integration to the end and
concentrates risk exactly where there is no time left to absorb it.

------------------------------------------------------------------------------
1.3 Definition of Done, Applied Per Task
------------------------------------------------------------------------------

A task is done when all six hold:

  1. The behaviour works on the happy path.
  2. At least one failure path is handled and produces a comprehensible error.
  3. Any rule the task implies is expressed as a database constraint where it
     is expressible as one.
  4. An automated test exercises both a success and a failure case.
  5. The relevant documentation section is written or amended.
  6. The code is committed with a message naming the requirement identifier it
     satisfies.

Point 3 is the one most often skipped and the one that most distinguishes this
project from a typical submission. Point 6 makes the traceability matrix a
by-product rather than a chore at the end.

------------------------------------------------------------------------------
1.4 Never Carry Broken Work Across a Phase Boundary
------------------------------------------------------------------------------

Each phase ends with a gate. Work that does not pass the gate is either
completed before the next phase begins or is formally descoped using the ladder
in section 15. Carrying half-finished work forward is how a project arrives at
its final week with six things at eighty percent and nothing to demonstrate.

2. ASSUMPTIONS, TEAM AND CALENDAR
================================================================================

------------------------------------------------------------------------------
2.1 Assumptions
------------------------------------------------------------------------------

  A1  Team of three, each contributing roughly 10 hours per week.
  A2  Ten calendar weeks available before submission.
  A3  All members have working SQL knowledge; one has prior web experience.
  A4  PostgreSQL 15 and Node 20 available on every machine, via Docker.
  A5  A shared Git repository with branch protection on the main branch.
  A6  Access to a list of campus buildings and rooms for seeding.
  A7  No external approval gates that could block progress.

------------------------------------------------------------------------------
2.2 Roles
------------------------------------------------------------------------------

Roles are primary responsibilities, not exclusive territories. Every member
reviews outside their area, because a schema reviewed only by its author is a
schema with unreviewed assumptions.

  Member A — Data and query owner
      Schema, migrations, normalisation analysis, indexes, stored procedures,
      the matching engine, query plan evidence, seed data generation.

  Member B — Application and API owner
      Service layer, transaction orchestration, controllers, authentication,
      authorisation, error mapping, API tests.

  Member C — Interface and evidence owner
      Design system, React components, screens, accessibility, the
      documentation set, the demonstration script and rehearsal.

------------------------------------------------------------------------------
2.3 Calendar
------------------------------------------------------------------------------

  Week   Phase                                    Gate
  -----  ---------------------------------------  -------------------------
  1–2    Phase 1 — Foundation and Data Model      Schema gate
  3–4    Phase 2 — Core Domain and Matching       Matching gate
  5–6    Phase 3 — Claims, Transactions, Audit    Transaction gate
  7–8    Phase 4 — Interface and Experience       Usability gate
  9–10   Phase 5 — Hardening and Delivery         Release gate

Total effort: roughly 300 person-hours. The estimate assumes learning time is
included and that some of it is spent badly, which it always is.

------------------------------------------------------------------------------
2.4 Working Agreements
------------------------------------------------------------------------------

Daily fifteen-minute synchronisation, asynchronous if necessary: what I did,
what I am doing, what is blocking me.

All work on branches named by requirement identifier. Merge to main only through
a reviewed pull request. Main is always in a demonstrable state — a broken main
on the day before a review is an avoidable disaster.

No manual schema changes, ever. If it is not in a migration it does not exist.

A decision that is debated for more than twenty minutes is written down as a
decision record and moved on from. The cost of the wrong choice is almost always
lower than the cost of the argument.

4. PHASE 1 — FOUNDATION AND DATA MODEL
================================================================================
Weeks 1–2 · ~60 person-hours

------------------------------------------------------------------------------
4.1 Objective
------------------------------------------------------------------------------

Produce a complete, migrated, seeded, constrained relational schema, together
with the written normalisation analysis that justifies it. At the end of this
phase there is no application, and that is correct.

------------------------------------------------------------------------------
4.2 Task Breakdown
------------------------------------------------------------------------------

  T1.1  Repository, Docker Compose, PostgreSQL 15, migration tooling      4h  A
        Exit: `npm run migrate` applies zero migrations without error on a
        fresh database.

  T1.2  Requirements consolidation and entity identification               6h  All
        Read the PRD together. List candidate entities. Argue about them.
        Produce the agreed entity list with one-line responsibilities.
        Exit: a written entity inventory all three members agree with.

  T1.3  ER diagram, conceptual                                             6h  A, C
        Entities, relationships, cardinalities, participation. Drawn, not
        described. Include the two-role USERS-to-CLAIMS relationship and the
        CATEGORIES self-reference, because they are the two constructs an
        examiner will ask about.
        Exit: a diagram file in the repository.

  T1.4  Functional dependency analysis                                     8h  A
        For each relation: attribute set, non-trivial FDs, attribute closures,
        candidate keys, prime attributes.
        This is the task most likely to be rushed and the one that most repays
        being done properly. It is the evidence for Module 2.
        Exit: the FD document with closures shown, not asserted.

  T1.5  Normalisation to 3NF with the decomposition narrative              6h  A
        Start from the unnormalised REPORT_RAW relation. Show the 1NF failure
        (status_history as a repeating group). Show the four transitive
        dependencies. Decompose. Then find and address the matches
        score→band violation, presenting all three candidate responses and the
        chosen one.
        Exit: the normalisation section of the TRD, complete.

  T1.6  Enumerated types and reference tables migration                    4h  A
        001_types.sql, 002_reference_tables.sql.
        Exit: types and six reference relations exist.

  T1.7  Core relations migration                                           8h  A
        003_users.sql, 004_items.sql, 005_matches_claims.sql, 006_audit.sql.
        Every constraint from TRD section 5, named per Appendix C.
        Exit: `\d+` on every table shows the expected constraints.

  T1.8  Referential action decisions                                       3h  A, B
        For each of the fourteen foreign keys, decide and record ON DELETE.
        Do not default everything to CASCADE, which is the lazy answer and the
        wrong one for eleven of the fourteen.
        Exit: the referential policy table in the TRD.

  T1.9  Reference data seeding                                             5h  A
        Twenty categories with their requires_staff and is_sensitive flags,
        eighty locations with building and zone, twenty-five colours with hex
        values, sixty brands, three score bands, twelve config rows.
        Exit: `npm run seed:reference` is idempotent and complete.

  T1.10 Synthetic data generator                                           6h  A
        Not uniform random. Category frequency long-tailed, location frequency
        concentrated, dates clustered around term dates. Parameterised by
        volume so the same script produces the 100-row development set and the
        20,000-row performance set.
        Exit: `npm run seed:data -- --lost 1000 --found 400` works.

  T1.11 Constraint test suite                                              6h  A, B
        One test per constraint, attempting the violation and asserting the
        SQLSTATE. Roughly forty tests.
        Exit: all pass; commenting out any constraint makes exactly one fail.

  T1.12 Phase 1 documentation                                             4h  C
        ER diagram, data dictionary, FD analysis, normalisation narrative,
        referential policy — assembled and readable.

------------------------------------------------------------------------------
4.3 Schema Gate
------------------------------------------------------------------------------

  [ ] Migrations apply cleanly from empty and roll back cleanly
  [ ] Every relation has a primary key
  [ ] Every foreign key declares an explicit ON DELETE, decided not defaulted
  [ ] Every status column is domain-constrained
  [ ] Every date column that can be wrong has a CHECK
  [ ] The three biconditional consistency CHECKs exist
  [ ] Reference seed is idempotent
  [ ] Synthetic generator produces realistic distributions
  [ ] All constraint tests pass
  [ ] FD analysis exists with closures computed
  [ ] 3NF argued per relation, and the matches violation found and addressed
  [ ] Every team member can explain any constraint in the schema

The last item is the real gate. A schema that only one member understands is a
schema that will be defended by one member in a viva.

------------------------------------------------------------------------------
4.4 Common Failure Modes in This Phase
------------------------------------------------------------------------------

Treating normalisation as a formality to be written up afterwards. The analysis
must precede the DDL, or the DDL will encode an unexamined design and the
write-up will be a rationalisation.

Making location a VARCHAR because it is faster to type. This single decision
destroys matching, analytics and filtering simultaneously, and it is the most
common defect in projects of this kind.

Defaulting every foreign key to ON DELETE CASCADE. Cascade is correct for
matches and wrong for the other eleven. A cascade from users would silently
delete a person's entire history.

Skipping the synthetic generator and hand-typing twenty rows. Twenty rows make
every index look unnecessary and every query look fast. The performance work in
Phase 2 becomes impossible.

5. PHASE 2 — CORE DOMAIN AND THE MATCHING ENGINE
================================================================================
Weeks 3–4 · ~65 person-hours

------------------------------------------------------------------------------
5.1 Objective
------------------------------------------------------------------------------

Reports can be created through an API, and matches are generated correctly,
explainably and within budget. This is the phase in which the product's central
claim becomes true.

------------------------------------------------------------------------------
5.2 Task Breakdown
------------------------------------------------------------------------------

  T2.1  Application skeleton and layering                                  5h  B
        Express, the middleware chain in its fixed order, the connection pool,
        the withTransaction helper, the error middleware, structured logging
        with request ids.
        Exit: `GET /api/v1/health` returns database connectivity status.

  T2.2  Authentication                                                     8h  B
        Registration with bcrypt at cost 12, sign-in with timing equalisation,
        JWT issue and verification, refresh tokens in a sessions relation,
        role middleware.
        Exit: register, sign in, call a protected route, sign out, and find the
        refresh token revoked.

  T2.3  Reference data endpoints                                           3h  B
        Read endpoints for the four vocabularies, loaded into memory at boot
        with invalidation on admin write.
        Exit: reference data served from cache, one query at boot.

  T2.4  Lost report creation                                               6h  B
        Validation, repository, service, controller. Transaction wrapping the
        insert and the audit row.
        Exit: POST /lost-items creates a row and an audit row atomically; every
        constraint violation maps to a specific error code.

  T2.5  Found report creation                                             6h  B
        As above, plus the custody conditional, the private field, and the
        private-duplicates-public service check.
        Exit: as above, plus the conditional storage requirement enforced.

  T2.6  Matching procedure, forward direction                             10h  A
        generate_matches_for_lost in full: config reads, pre-filters, scoring
        expression, band join, reason_json construction, ON CONFLICT.
        Exit: called with a known anchor against a known fixture set, produces
        exactly the hand-computed scores.

  T2.7  Matching procedure, reverse direction                              4h  A
        generate_matches_for_found, with the date predicate oriented so the
        lost-side index remains usable.
        Exit: symmetric correctness verified on the same fixtures.

  T2.8  Twenty-pair verification fixture                                   5h  A
        Twenty lost-found pairs with scores computed by hand on paper, spanning
        the difficulty range and including the edge cases: zero-day gap,
        found-before-lost, all-nulls-on-optionals, exactly-at-floor.
        Exit: an automated test asserting all twenty, passing.

  T2.9  Match generation wired into report creation                        3h  A, B
        The procedure call inside the creation transaction, and the top-match
        read-back for the response.
        Exit: creating a report returns matches_generated and top_match.

  T2.10 Match retrieval endpoints                                          5h  B
        Ranked list for a lost item with the ownership predicate in the WHERE
        clause; single match detail; dismissal.
        Exit: requesting another user's matches returns 404, not 403.

  T2.11 Index design with measured evidence                                8h  A
        Seed to 10,000 and 10,000. EXPLAIN ANALYZE the match query. Capture the
        sequential-scan plan. Create ix_found_match_probe and ix_lost_match_
        probe. Capture the bitmap-scan plan. Record both, with buffer counts.
        Then deliberately create the wrong-column-order index and show that the
        planner declines it.
        Exit: three plans captured in the repository with commentary.

  T2.12 Browse and search                                                  6h  B
        Dynamic predicate construction with bound parameters, the allow-listed
        sort map, count(*) OVER () for the total, full-text search via the
        generated tsvector columns and GIN indexes.
        Exit: filters combine correctly; no user string reaches SQL text.

  T2.13 Phase 2 documentation                                              4h  C
        Matching specification, scoring rubric with worked examples, the index
        evidence with before-and-after plans and the anti-pattern.

------------------------------------------------------------------------------
5.3 Matching Gate
------------------------------------------------------------------------------

  [ ] All twenty fixture pairs score exactly as hand-computed
  [ ] Found-before-lost scores zero on the temporal component
  [ ] Null optionals award zero and are not penalised further
  [ ] Sparse pairs correctly cap below 100
  [ ] reason_json components sum exactly to the stored total, always
  [ ] Re-running generation is idempotent; no duplicate rows
  [ ] Re-running does not overwrite a match past SUGGESTED
  [ ] A user is never matched to their own report
  [ ] Match generation under 200 ms at 10k × 10k
  [ ] Before-and-after EXPLAIN captured with buffer counts
  [ ] The wrong-column-order index demonstrably not chosen
  [ ] Matches row count under 8× lost item count after seeding
  [ ] Ownership enforced in the WHERE clause, not in application code

------------------------------------------------------------------------------
5.4 Common Failure Modes in This Phase
------------------------------------------------------------------------------

Computing the temporal component from created_at rather than from the event
dates. Produces a system that quietly punishes users for reporting late, and the
defect is invisible until someone reports a week-old loss.

Writing the anchor predicate as a join condition rather than in the WHERE
clause. Produces a hash join over the whole table. The query still returns
correct results, so nothing fails — it is just twenty times slower, forever.

Recomputing the score on the client for display. Guarantees a divergence the
first time a weight changes.

Building the browse filters with string concatenation. Works, demonstrates
nothing, and is an injection vector.

Testing matching only with rich fixtures where every attribute is populated. The
null-handling paths are exactly where the bugs are.

6. PHASE 3 — CLAIMS, TRANSACTIONS AND AUDIT
================================================================================
Weeks 5–6 · ~60 person-hours

------------------------------------------------------------------------------
6.1 Objective
------------------------------------------------------------------------------

The full lifecycle from report to return works through the API, is safe under
concurrency, and leaves a complete history. This phase contains the project's
strongest single piece of evidence for Module 4.

------------------------------------------------------------------------------
6.2 Task Breakdown
------------------------------------------------------------------------------

  T3.1  Audit service                                                      5h  B
        A single function used by every state-changing transaction, taking the
        client so the write joins the caller's transaction rather than opening
        its own.
        Exit: no code path writes audit_log except through this function.

  T3.2  Audit immutability                                                 2h  A
        Privilege revocation on the application role plus the belt-and-braces
        trigger.
        Exit: UPDATE and DELETE on audit_log fail as the application role.

  T3.3  Denormalised found_id on claims with its trigger                   4h  A
        The column, the foreign key, the BEFORE INSERT trigger, and the
        alphabetical-ordering comment explaining why the trigger is named as
        it is.
        Exit: inserting a claim populates found_id automatically; a mismatch
        is impossible.

  T3.4  The partial unique index                                           2h  A
        ux_one_approved_claim_per_found on claims(found_id) WHERE status IN
        ('APPROVED','COMPLETED').
        Exit: two approved claims on one found item cannot exist, even with
        every application check removed.

  T3.5  Claim creation                                                     6h  B
        The five guards in ascending cost order, the combined ownership and
        availability query, the transaction, the match status transition.
        Exit: claiming your own find is refused by the trigger; a fourth
        pending claim is refused by the service.

  T3.6  approve_claim procedure                                           10h  A, B
        The nine steps of TRD section 10.2, in the fixed lock order, with the
        locking read before the trusted read.
        Exit: approval updates claim, found item, lost item, competing claims,
        matches and audit atomically.

  T3.7  reject_claim and escalation                                        4h  B
        Rejection with a canned reason, match returned to SUGGESTED, claimant
        flagged_count incremented — but not for a systemic rejection produced
        by step 7 of an approval, which is a distinction that must be coded
        explicitly.
        Exit: the two rejection paths are distinguishable in the data.

  T3.8  complete_handover                                                  4h  B
        The three-relation update with the biconditional CHECKs as the guard,
        FOR UPDATE OF scoped to the claims row only.
        Exit: a status update without its timestamp fails at write time.

  T3.9  Concurrency test, automated                                        8h  A, B
        Two connections, explicit synchronisation, both approving different
        claims on one found item. Assert exactly one APPROVED. Then a fifty-way
        version. Then the same test with FOR UPDATE removed, asserting the
        failure, kept as a disabled test with a comment.
        Exit: the passing test is in CI; the failing variant is documented.

  T3.10 Deadlock ordering audit                                            3h  A
        Walk every multi-relation transaction and confirm the global lock
        order. Document it as a development standard.
        Exit: the ordering rule written down and every transaction conforms.

  T3.11 Audit timeline endpoint                                            4h  B
        The v_item_timeline query with the audit_id tiebreaker, and the party
        authorisation check.
        Exit: three rows from one transaction display in insertion order.

  T3.12 Audit consistency test                                             3h  A
        Query Q8 as an automated test asserting zero rows, run against the
        seeded dataset after a scripted full lifecycle.
        Exit: passes; deliberately corrupting a status makes it fail.

  T3.13 Expiry job                                                         4h  A
        Batched at 500 with SKIP LOCKED, audited with a null actor.
        Exit: runs, expires, does not block a concurrent user transaction.

  T3.14 Phase 3 documentation                                              4h  C
        Transaction design, ACID analysis against this specific transaction,
        the isolation level argument, deadlock prevention, the concurrency
        demonstration script.

------------------------------------------------------------------------------
6.3 Transaction Gate
------------------------------------------------------------------------------

  [ ] Fifty concurrent approvals on one item: exactly one succeeds
  [ ] The forty-nine failures return ITEM_NOT_AVAILABLE, not a generic 500
  [ ] With FOR UPDATE removed, the partial unique index still prevents the
      double approval — verified, because defence in depth that has not been
      tested is a claim, not a defence
  [ ] Every audit write is inside its change's transaction
  [ ] A rolled-back change leaves no audit row
  [ ] audit_log is not updatable or deletable by the application role
  [ ] Audit consistency query returns zero rows
  [ ] Lock ordering is global and documented
  [ ] The full lifecycle runs end to end through the API
  [ ] The two-session psql demonstration is scripted and rehearsed
  [ ] Every member can explain the transaction's ACID properties in terms of
      this transaction, not in general

------------------------------------------------------------------------------
6.4 Common Failure Modes in This Phase
------------------------------------------------------------------------------

Reading the status before taking the lock. The most common concurrency error
there is, and it leaves the original race window fully open while looking like a
fix.

Writing audit rows in a separate transaction. Produces exactly the orphans the
consistency query exists to find.

Approving without re-verifying status under the lock. The lock alone does not
help if the decision was made on a value read before it.

Incrementing flagged_count on systemic rejections. Punishes a user for losing a
race they never entered.

Locking every row produced by a join. Widens the lock footprint and creates a
deadlock opportunity with the approval transaction, which locks found_items
first.

------------------------------------------------------------------------------
7.3 Usability Gate
------------------------------------------------------------------------------

  [ ] All MVP flows completable in a browser end to end
  [ ] Lost report under ninety seconds, timed, five first-time testers
  [ ] Every screen has designed empty, loading and error states
  [ ] The private field's purpose is understood by testers without prompting
  [ ] Match reasons visibly sum to the score
  [ ] The 409 conflict message reads as an explanation, not a failure
  [ ] Keyboard-only completion of both core journeys
  [ ] Screen-reader completion of both core journeys
  [ ] Contrast verified and recorded for every text/background pair
  [ ] No horizontal scroll at 360 px on any screen
  [ ] No hard-coded colour or spacing value in any component
  [ ] No private field present in any public response payload

------------------------------------------------------------------------------
7.4 Common Failure Modes in This Phase
------------------------------------------------------------------------------

Building screens before the component library. Produces fifteen slightly
different buttons and a week of reconciliation.

Placeholder-as-label. Saves vertical space and costs comprehension for anyone
interrupted mid-form.

Leaving empty states until last. They are the most-seen state in a new system
and they will be written carelessly at 2 a.m. if deferred.

Treating accessibility as a retrofit. Focus management and semantic structure
are cheap to build in and expensive to add afterwards.

Letting a private field into a response payload because it was already on the
object. This is why the privacy test exists and why public reads go through the
view.

8. PHASE 5 — HARDENING, EVIDENCE AND DELIVERY
================================================================================
Weeks 9–10 · ~50 person-hours

------------------------------------------------------------------------------
8.1 Objective
------------------------------------------------------------------------------

Every claim made anywhere in the documentation is backed by a measurement, and
the demonstration runs end to end without intervention.

------------------------------------------------------------------------------
8.2 Task Breakdown
------------------------------------------------------------------------------

  T5.1  Evaluation dataset construction                                    8h  A
        Two hundred lost, two hundred found, sixty ground-truth pairs across
        three difficulty tiers. Version-controlled with the code.
        Exit: `npm run seed:eval` reproduces it exactly.

  T5.2  Measure SC1 and SC2                                                5h  A
        Recall at top-3 across the sixty pairs; precision among pairs scoring
        80 or above. Record the numbers.
        Exit: both measured; if either misses, tune weights against this
        dataset and re-measure, recording each iteration.

  T5.3  Measure SC3 through SC7                                            5h  A, B
        Latency at volume, adversarial claim rejection across twenty trials,
        audit completeness, the fifty-way concurrency test, and an external
        review of 3NF compliance by a member who did not write the schema.
        Exit: a results table with measured values against thresholds.

  T5.4  Performance sweep                                                  5h  A
        Every budgeted operation, ten runs, first discarded, median recorded,
        plan captured.
        Exit: a budget-versus-actual table; any miss investigated, not
        explained away.

  T5.5  Security review                                                    4h  B
        Grep for string-concatenated SQL. Verify every public endpoint against
        the private-field deny list. Confirm rate limits fire. Confirm the
        application role holds no DDL privilege. Confirm no secret in the
        repository history, not merely in the current tree.
        Exit: a findings list, empty or remediated.

  T5.6  Test suite completion                                              6h  All
        Constraint tests, query tests, transaction tests, API tests, privacy
        tests. Every endpoint with at least three. Every constraint with a
        negative test.
        Exit: full suite green from a clean database in one command.

  T5.7  Backup and restore rehearsal                                       2h  A
        pg_dump, restore into a scratch database, verify row counts and run
        the consistency query.
        Exit: a restored backup passes the same tests as the original.

  T5.8  Documentation assembly                                             8h  C
        All five documents complete and consistent. Traceability matrices
        checked. Screenshots current. Diagrams legible when printed.
        Exit: a reviewer can trace any requirement to its implementation.

  T5.9  Demonstration script                                               4h  All
        Written beat by beat with timings, the narrative dataset prepared, the
        two-session concurrency demonstration scripted, fallback screenshots
        captured for every step in case something fails live.
        Exit: the script exists and names who speaks when.

  T5.10 Rehearsal                                                          3h  All
        Twice, end to end, on the demonstration machine, timed.
        Exit: two clean runs without intervention.

8.4 Common Failure Modes in This Phase
------------------------------------------------------------------------------

Tuning weights against a single anecdotal mismatch. Overfits to one example and
silently degrades the general case. Tune only against the evaluation dataset and
record each iteration.

Writing documentation from memory in week ten. Every phase writes its own
documentation section as it goes; Phase 5 assembles, it does not author.

Demonstrating on data typed live. Prepare the narrative dataset and rehearse
against it.

Rehearsing on a developer machine and presenting on another. Rehearse where you
will present.

9. CROSS-PHASE WORKSTREAMS
================================================================================

------------------------------------------------------------------------------
9.1 Documentation
------------------------------------------------------------------------------

Each phase writes its own sections. Phase 1 writes the data model and
normalisation. Phase 2 writes matching and indexing. Phase 3 writes transactions
and concurrency. Phase 4 writes the design system and flows. Phase 5 assembles
and checks consistency. Documentation deferred entirely to the end is
documentation written badly.

------------------------------------------------------------------------------
9.2 Testing
------------------------------------------------------------------------------

Tests are written with the feature, not after the phase. The constraint suite
begins in Phase 1 and grows. A phase gate cannot pass with failing tests.

------------------------------------------------------------------------------
9.3 Review
------------------------------------------------------------------------------

Every pull request is reviewed by someone outside the author's primary area.
This is the mechanism by which all three members end up understanding the whole
system, which is the actual requirement in a viva.

------------------------------------------------------------------------------
9.4 Decision Records
------------------------------------------------------------------------------

Any decision with a plausible alternative gets a short record: what was decided,
what was rejected, why, and what it costs. Eight exist already in the Tech Flow
document. Adding to them as decisions arise makes the final documentation a
collection rather than a composition.

12. QUALITY GATES
================================================================================

------------------------------------------------------------------------------
12.1 Continuous Requirements
------------------------------------------------------------------------------

Main is always demonstrable. A commit that breaks main is reverted, not fixed
forward, unless the fix is under ten minutes.

All work through reviewed pull requests. Self-merging defeats the cross-review
mechanism that makes every member able to defend the whole system.

No schema change outside a migration. No exceptions, including "just for
testing".

No commit containing a secret. A pre-commit hook scanning for key patterns costs
ten minutes to add and prevents a mistake that cannot be undone once pushed.

14. DEMONSTRATION PLAN
================================================================================

Fifteen minutes, structured so that the database work occupies the majority of
the time, because it occupies the majority of the marks.

  0:00–1:30   The problem, in concrete terms
              Two reports, two channels, never meeting. State the project
              statement verbatim. No slides beyond one.

  1:30–4:00   The data model
              ER diagram. Walk the relationships. Then the normalisation: the
              unnormalised relation, the location transitive dependency, the
              decomposition. Then the matches score→band violation, the three
              candidate responses, and the one chosen. This is the strongest
              two minutes available and it is placed early.

  4:00–7:00   Matching, live
              File a lost report. Show it returns no matches and the
              standing-query message. File the corresponding found report from
              a second browser. Return to the first, refresh, show the 98.
              Open the reason breakdown and add the numbers aloud.
              Then drop to psql and show the same match row, its reason_json,
              and the procedure that produced it.

  7:00–10:00  Transactions, live
              Two psql sessions side by side. Session 1 takes the lock.
              Session 2 blocks visibly. Session 1 commits. Session 2 unblocks
              and fails with ITEM_NOT_AVAILABLE.
              Then the same sequence with FOR UPDATE removed, producing two
              approved claims. Then show the partial unique index catching it
              anyway.

  10:00–12:00 Indexing
              EXPLAIN ANALYZE before: 313 ms, 9,958 rows removed by filter.
              Create the index. After: 29 ms, 47 buffers. Then the
              wrong-column-order index that the planner declines, and why.

  12:00–13:30 Audit and analytics
              The timeline for the item just returned. Then the hotspot view
              with its window functions, and the point that the divergence
              between lost and found locations is the actionable output.

  13:30–15:00 Questions

  Preparation
    Narrative dataset loaded and verified the morning of.
    Both browsers signed in as the two personas, on separate profiles.
    Two psql sessions open with the commands in scrollback.
    Screenshots of every step, in order, on a second device.
    A rehearsed answer to "why no AI?" — because attribute matching is
    sufficient for commodity objects, is explainable line by line, and the
    project's purpose is to demonstrate the database rather than to hide it
    behind a model.

15. CONTINGENCY AND DESCOPING LADDER
================================================================================

------------------------------------------------------------------------------
15.1 The Ladder
------------------------------------------------------------------------------

If time runs short, descope in this order. Each rung is chosen because it
removes work without removing evidence.

  1.  Analytics dashboard interface. Keep the views; demonstrate them in psql.
      Costs a screen, keeps every window function and aggregate.
  2.  Staff console screens. Keep the endpoints and the staff verification
      routing. Demonstrate via API.
  3.  Browse filters beyond category and date.
  4.  Full-text description matching. Fall back to the manual token
      intersection, or drop the component and rescale the rubric to 90.
  5.  Expiry job. Document the design; do not build it.
  6.  Match dismissal.
  7.  Editing reports after creation.

------------------------------------------------------------------------------
15.2 Never Descope
------------------------------------------------------------------------------

  The normalisation analysis. It is Module 2 in its entirety.
  The matching engine and its reason breakdown. It is the product.
  The approval transaction and its concurrency test. It is Module 4 in its
    entirety, and it is the single best piece of evidence the project has.
  The audit trail. It is the integrity story and the temporal-database angle.
  The index evidence. It is Module 3, and it takes one afternoon.
  The constraint suite. It is what makes every claim about integrity
    verifiable rather than asserted.

------------------------------------------------------------------------------
15.3 If a Phase Slips
------------------------------------------------------------------------------

Phase 1 slipping is the most dangerous case, because everything depends on it.
Response: extend Phase 1 by up to three days and take the time from Phase 4,
descending the ladder as needed. A correct schema delivered late beats a rushed
schema delivered on time, because a rushed schema costs more in Phases 2 and 3
than it saves in Phase 1.

Phase 2 slipping: take time from Phase 4. The interface can be plain.

Phase 3 slipping: do not take time from testing. Take it from Phase 4 and
descope aggressively. The concurrency evidence is worth more than any screen.

Phase 4 slipping: descend the ladder. The API-level demonstration is acceptable
for anything below rung 2.

Phase 5 slipping: it cannot. Phase 5 is measurement and rehearsal, and a project
that skips those arrives at its review with untested claims and an unrehearsed
demonstration. If Phase 5 is under pressure, the correct response is to have
descoped earlier.
